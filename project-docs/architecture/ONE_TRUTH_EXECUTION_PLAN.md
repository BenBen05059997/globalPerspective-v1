## Phase 1 — The shared-module drift guard (`scripts/check-shared-sync.mjs`)

This phase creates **one new script**. It does not touch any file under `amplify/backend/function/`, including the 4 pairs it guards — deliberately: adding even header comments to those function dirs would create repo≠deployed drift (those functions are hand-deployed, not built from repo source on every deploy) for zero behavioral gain. The script only reads and compares.

### Step 1.1 — Build the script

Guard exactly these 4 verified pairs:

**a. `riskDimensions.js` — byte-identical, zero tolerance.**
`amplify/backend/function/newsCountryIntelligence/src/riskDimensions.js` vs `amplify/backend/function/newsThreadAnalysis/src/riskDimensions.js`. Plain diff. Any difference is drift.

**b. `situations-core.js` — known 2-line header tolerance, anchored.**
`amplify/backend/function/newsSituationTracker/src/situations-core.js` vs `amplify/backend/function/newsGdacsIngest/src/situations-core.js`. The Tracker copy carries exactly this 2-line header comment that the Ingest copy lacks:
```
⚠️ SHARED MODULE — keep byte-identical with newsGdacsIngest/src/situations-core.js.
(Manual-deploy repo has no Lambda layers; sync by hand. Canonical: DATA_STRATEGY.md.)
```
The tolerance **must be anchored to this literal text**, not to a line-count threshold — pressure-testing found that a generic "≤2 lines different is OK" rule would silently pass a real 2-line drift elsewhere in the file. Implementation: strip exactly this literal 2-line block (if present at the top of the Tracker copy) before diffing; any remaining difference is drift.

**c. `country_facts.json` — metadata-field exclusion, structural compare.**
`amplify/backend/function/newsCountryIntelligence/src/country_facts.json` vs `amplify/backend/function/newsPairIntelligence/src/country_facts.json`. Known benign diff = the `description` and `sync` metadata fields (each file's copy names its sibling in these fields). Tolerance: parse both as JSON, deep-compare every field **except** `description` and `sync`, which must merely **exist** (not be compared for equality) in both.

**d. Entity-normalization block vs file — `require()` and compare exports, not text.**
`amplify/backend/function/newsSituationIngest/src/classifier-core.js` (the entity-normalization block, lines ~85-121) vs `amplify/backend/function/NewsProjectInvokeAgentLambda/src/entity-normalize.js`. This is a block inside a larger file compared against a whole file, so a plain text/line diff is impossible — pressure-testing flagged this explicitly. Mechanism:
- `require()` both modules directly (`classifier-core.js` is documented pure — "NO AWS, NO network" — safe to load in a script context).
- Compare, with exact string equality:
  - `normalizeEntity.toString()` (the function source, from both modules)
  - `JSON.stringify(ACTOR_ALIASES)` (both modules)
  - `.source` of `ENTITY_TITLE_PREFIX` and `.source` of `ENTITY_ORG_SUFFIX` (the regex patterns, both modules)
- Any inequality on any of the four comparisons is drift.

**Script behavior (all pairs):**
- Prints one PASS/DRIFT line per pair; on DRIFT, prints the offending diff (or the specific unequal field, for pair d).
- Exit code 0 if all 4 pairs PASS; exit code 1 if any pair DRIFTs.
- Runnable standalone: `node scripts/check-shared-sync.mjs`.
- No dependencies beyond Node stdlib (no npm install required to run it).

### Step 1.2 — Verify (two-sided)

**Positive:** run `node scripts/check-shared-sync.mjs` against the live repo — all 4 pairs must PASS today (this is the current, verified-clean state).

**Negative (the guard must be seen failing at least once):** copy one pair into a temp directory, perturb one byte in one copy, and point the script at the perturbed paths — confirm it reports DRIFT and exits 1. Support this via either:
- an env var or CLI arg that overrides the paths the script checks, or
- a `--self-test` mode that performs this perturb-and-check automatically for all 4 pairs.

Do both halves of this verification before considering Phase 1 done. A guard that has never been observed to fail is not a verified guard.

## Phase 3 — Severity benchmark (codebook + gold set + agreement baseline)

### Step 3.1 — Write `SEVERITY_CODEBOOK.md`

Create `project-docs/architecture/SEVERITY_CODEBOOK.md`: the anchored labeling rubric.

Contents:
- **4 axes** — conflict / political / economic / humanitarian — defined exactly as the generators currently define them. Quote the current one-line axis definitions verbatim from `amplify/backend/function/newsCountryIntelligence/src/index.js` (~line 487-492) and `amplify/backend/function/newsThreadAnalysis/src/index.js` (~line 263) as the codebook's starting point (read, do not edit those files).
- **4 bands per axis** — low 0-24 / moderate 25-49 / elevated 50-74 / high 75-100.
- **2-3 concrete worked anchor examples per band per axis** (i.e. ~8-12 worked examples per axis, ~32-48 total) — real or realistic scenarios illustrating what belongs in each band.
- **The null rule:** no signal on an axis → the axis is `null`, never `0`. Document this explicitly since it's the most common labeling error.
- **Worst-axis-wins:** the overall severity for a record is its highest-scored axis, not an average.
- **Labeling instructions for the operator** (used directly in Step 3.4).

The prompt text itself is read-only source material here — **the prompt is not touched.** This step produces a doc only.

**ADDENDUM 2026-09-15:** baseline complete (`quality/calibration/severity-2026-09-14.md`); the hard rule is satisfied and Phase 4 (below) now authorizes the measured prompt change.

**Verification:** review the codebook against the actual live prompt text it quotes (side-by-side read) to confirm the quoted definitions are accurate and current, not paraphrased or stale.

### Step 3.2 — Build `pick_severity_sample.js`

Create `quality/pick_severity_sample.js` (snake_case filename, per existing `quality/` convention — modeled on `quality/pick_weekly_review.js`).

**Sampling:** ~25-30 records from DynamoDB, drawn from both `COUNTRY#<name>/COUNTRY_INTELLIGENCE` and `THREAD#<id>/THREAD_ANALYSIS` item types (live/current records, not history snapshots — see freezing rule below for why).

**Critical constraints (pressure-test findings):**

1. **Freeze on read — one live read per record, never re-read later.** For each sampled record, capture in a single read: the narrative fields (`headline`/`bluf`/`keyDevelopments` for country records, or `threadTitle`/`storyArc`/etc. for thread records) **and** the exact `dimensions`/`riskScore` object from that same read, into the sample file. Do not re-read live data afterward — these DDB items are overwritten daily by the generators, so a later read would silently swap in a different record's data under the same id. Dated `HISTORY#` snapshots do carry scores but carry **no narrative**, so they cannot substitute — a record must be captured live, in full, once.

2. **Exclude the DeepSeek-outage window.** Filter candidate records by `generatedAt`, excluding `2026-09-13T00:00Z` through the 2026-09-15 top-up (i.e. keep only records generated before the outage started or after recovery). Records generated during the outage are not representative of normal generator behavior.

3. **Check null-rate before fixing sample size.** Before finalizing the sample, print the per-axis null-rate across all candidates. If most axes are null on most candidate records, **stratify** the sample (oversample multi-axis / high-severity records) so that each axis ends up with a meaningful labeled n — a sample dominated by null axes produces an agreement baseline with no statistical content.

**Output:** `quality/severity_gold_set.json` — a JSON array, one entry per sampled record:
```json
{
  "id": "...",
  "type": "country | thread",
  "sampledAt": "...",
  "generatedAt": "...",
  "narrative": { "...frozen fields as described above..." },
  "model_dimensions": { "conflict": ..., "political": ..., "economic": ..., "humanitarian": ..., "riskScore": ... },
  "gold": { "conflict": null, "political": null, "economic": null, "humanitarian": null },
  "gold_why": {}
}
```
`gold` and `gold_why` are left for the operator to fill in Step 3.4. Structure `model_dimensions` to sit **last** in each record (or otherwise out of the operator's immediate view while labeling) and note in the labeling instructions (Step 3.1) not to peek at it before labeling `gold`. Document this honestly in the codebook and in this plan as a **soft blind, not a real one** — the operator authored/reviewed the generator prompts and can recognize model output; this reduces but does not eliminate anchoring.

**Verification:** spot-read 3 entries from the generated `severity_gold_set.json` and confirm: (a) each has enough narrative content to actually judge severity from, (b) none falls inside the excluded outage window, (c) the per-axis null-rate was printed during the run and, if high, stratification visibly changed the sample composition.

### Step 3.3 — Build `severity_agreement.js`

Create `quality/severity_agreement.js`. Reads **only** `quality/severity_gold_set.json` — no live DDB reads (the frozen `model_dimensions` vs. the operator-filled `gold` is the entire comparison; this script never touches the database).

**Computes:**
- Exact-band agreement % (per axis and overall)
- Within-one-band agreement % (per axis and overall)
- Worst-axis-match % (does the model's and operator's worst axis agree)
- Per-axis n (how many records had a non-null gold label on that axis)

**Output:** a dated markdown report at `quality/calibration/severity-YYYY-MM-DD.md`, stamped with the model id(s) and the generation-date range found in the sample.

**Guard:** the script must refuse to run (printing a count of how many `gold` labels are still `null`/incomplete) if labeling is not yet finished — it must not silently compute an agreement score over a partially-labeled set.

**Verification:** before the first real run, hand-construct a small toy `severity_gold_set.json` (a handful of records with known agreement/disagreement) and confirm the script's computed percentages match a hand calculation.

### Step 3.4 — Operator: label the sample (~2h)

The operator (human) fills in `gold` and `gold_why` for every record in `severity_gold_set.json`, using `SEVERITY_CODEBOOK.md` as the rubric. This step is not performed by an executor agent.

### Step 3.5 — Run the agreement baseline

Once labeling is complete, run `node quality/severity_agreement.js`. Its output **is the baseline.**

**Hard rule (binding):** no prompt or rubric change to `newsCountryIntelligence` or `newsThreadAnalysis` before this baseline exists. The whole point of Phase 3 is to measure current model/operator agreement before touching anything that could change it.

**ADDENDUM 2026-09-15:** baseline complete (`quality/calibration/severity-2026-09-14.md`); the hard rule is satisfied and Phase 4 (below) now authorizes the measured prompt change.

## Phase 4 — Measured severity-prompt fix (added 2026-09-15, post-baseline)

**Purpose:** fix the three measured faults (systematic ~1-band inflation; null never used — 27 model-scored-where-judge-null vs 0 reverse; political axis conflating "involves politics" with "institutional instability", 23% exact) in the two severity generators — `newsCountryIntelligence` (deepseek-v4-pro) and `newsThreadAnalysis` (gemini-2.5-flash) — with improvement PROVEN OFFLINE before any deploy.

### Step 4.1 — Offline eval harness `quality/severity_prompt_eval.js`

Runs a CANDIDATE prompt over the frozen 28 narratives in `quality/severity_gold_set.json` (same inputs, same two model APIs as the graded baseline: deepseek-v4-pro via api.deepseek.com for country records, gemini-2.5-flash via the Gemini OpenAI-compatible endpoint for thread records), parses the dimensions JSON with the same normalization as `riskDimensions.js` (require it — do not reimplement), and grades against the gold labels with the SAME metrics as `severity_agreement.js` (exact-band %, within-one %, worst-axis match, per-axis n, PLUS the two inflation counters: model-higher-vs-judge-higher band counts, and model-scored-where-gold-null count).

API keys: fetched at runtime from the two Lambdas' env via AWS SDK GetFunctionConfiguration — NEVER printed, logged, or written to disk; keys live only in process memory.

Takes `--prompt-file <path>` (candidate rubric block) and `--label <name>`; writes results to `quality/calibration/prompt-eval-<label>-<date>.md`.

Also supports `--baseline-check`: runs the CURRENT live prompt text through the same offline path once, to verify the offline harness roughly reproduces the live baseline (sanity check that harness ≈ production behavior; expect similar, not identical, numbers — models are non-deterministic; document the delta).

### Step 4.2 — Candidate prompt v2

Drafted from `SEVERITY_CODEBOOK.md`: (i) the §2.5 axis-scope rulings condensed (political = DOMESTIC institutions only — being in a war / under sanctions / diplomatic pressure is NOT political; war and war-risk = conflict axis only; severity scores the PRESENT); (ii) 1-line band anchors per axis (condensed from §4 — the prompt must stay token-lean: ~15-20 added lines total, not the whole codebook); (iii) a firmer null rule ("if the record does not discuss the axis, output null — a scored axis REQUIRES a cited fact in why"). Keep everything else in the two prompts byte-identical to current.

The candidate lives in `quality/prompts/dimensions_v2_country.txt` + `dimensions_v2_thread.txt`.

### Step 4.3 — Iterate offline until the candidate BEATS baseline

Acceptance gates (all must hold on the frozen 28):
- political exact ≥ 45% (baseline 22.7%)
- model-scored-where-gold-null ≤ 10 (baseline 27)
- overall within-one ≥ 85% (no regression)
- no axis's within-one drops below baseline by >5 pts
- model-higher band-count ≤ 20 (baseline 41)

Maximum 4 iterations; if not met, STOP and report back to operator rather than deploying a non-improving prompt.
