# newsStoryRecord

The facts writer. Each run appends one UTC day's facts, with no model, to `record/facts/YYYY-MM-DD.jsonl` and writes that day's Run object to `record/runs/YYYY-MM-DD.json`. After the append it rebuilds the views under `record/views/` from every facts day ([decision 0037](../../../project-docs/decisions/0037-views-from-facts.md)). Format and rules: [decision 0036](../../../project-docs/decisions/0036-facts-file-format.md); design: [ARCHITECTURE_TIMELINE.md](../../../project-docs/architecture/ARCHITECTURE_TIMELINE.md) (§1c two clocks, §6 writers). Lines, chapters, branch status and confirmed links are readings written weekly by `newsRecordReview` (step 3); this Lambda is the only view builder and reads them (below).

## What a run does

1. Writes `runs/DATE.json` with `status:"started"` (a Run left at `started` with no `finishedAt` is the alarm).
2. Reads through shared `world/` only: `archive#` rows for the 30 days to DATE, the `today-archive` entries archived on DATE, the day's forecast snapshots (`FORECASTS_SOURCE=inbox`, live: `record/inbox/forecasts/`; `log` would read `PRED#` snapshots), the resolver's verdict inbox (`inbox/verdicts/`) and the merge and split inboxes (`inbox/merges/`, `inbox/splits/`) and the selector's article inbox (`inbox/articles/`) and the assignment inbox (`inbox/assignments/`) and the resolver's draws inbox (`inbox/draws/`), each the run day and 6 days before. No table is read for verdicts, no scan, no listing.
   Where the entries come from is `ENTRIES_SOURCE` (decision 0051): `archive` (default) reads `archive#` and `today-archive` as above; `inbox` reads `record/inbox/entries/DAY.jsonl` (the agent's lines, replayed to what the archive row ends the day as; `src/inboxEntries.js`, shared `entriesInbox.js`) for the 30-day window and the refresh, with no NewsCache read for entries; `compare` reads both, uses the archive and logs every difference as `[entries-compare]` (warn level when there is one). The inbox starts with the agent's first line: days before it are missing in `inbox` mode, so upload the CLI's 30-day backfill first (`backend/record/cli/build-entries-inbox.mjs`). `PRED#` snapshots are read through `FORECASTS_SOURCE` (decision 0052): `log` (default) is the PredictionLog Scan of the 30-day window (`dynamodb:Scan`, policy statement `PredictionLogScan`); `inbox` (live since 2026-11-02, after the 11-01 23:45Z compare had 0 differences over 647 snapshots) replays `record/inbox/forecasts/DAY.jsonl` (the agent's `drawn` and `thread` lines, shared `forecastsInbox.js`, `src/inboxForecasts.js`) to the same rows through `world.snapshotsOfRows`, with no table read; `compare` reads both, uses the log and logs every difference as `[forecasts-compare]`. The inbox starts with the agent's first line (earlier days are skipped in `compare`, missing in `inbox`): upload the CLI's backfill first (`backend/record/cli/build-forecasts-inbox.mjs`, which also proves the facts byte-identical). The refresh reads only today's inbox file (`<prefix>inbox/forecasts/<today>.jsonl`, `store.loadDayForecasts`), whatever `FORECASTS_SOURCE` says, and never scans the PredictionLog (below).
3. Builds facts and drops those already stored (it reads the last 100 days of fact files, so a re-run is a no-op and the same article listed again on a later day is not a second fact).
4. Appends each fact to the file of its own day (the UTC date of `at`), registers the days in `facts/manifest.json`, appends a `run` fact, and overwrites the Run with `ok`, `partial` or `failed`.
5. Throws when the Run is not `ok` (daily mode), so the schedule's Errors metric moves. A missing archive day is a `failed` Run with `inputs.archiveDay:"missing"`, never `ok`.

Not an entry: it is in no story and no index |
| `correction` | nothing yet | builder in `src/facts.js`; written when an operator input exists |
| `run` | the Run | appended every run, failures included |

IDs: [`record.js`](../../shared/src/record.js) (`canonicalUrl`, `entryIdentity`, `sourceIdOf`, `actorIdOf`, `factId`) and [`outlets.js`](../../shared/src/outlets.js) (`registrableDomain`, `TWO_LEVEL_SUFFIXES`). Missing inputs are recorded as missing: `iso3:[]` and `actorIds:[]` before about 2026-09-12, `summary:null`, `outlet:null` for an unknown outlet.

## Views

After the facts and before the Run is finalised, `src/publish.js` reads every day in `facts/manifest.json` (plus the days this invocation wrote), `src/views.js` (pure, no I/O) builds the view objects, and they are written with plain `PutObject` under `record/views/` (shadow: `record/shadow/views/`). A backfill builds once, after its last day. Write order, so a reader that sees a new manifest sees a complete set: `stories/*`, `links/*`, `counts/*`, `countries/*`, `briefs/daily/*`, `briefs/weekly/*`, then `index/active.json` (with `index/analyses.json`, `web.json`, `countries.json`, `weekly.json` and `briefs.json`, each over 2 MB fails the build like `all.json` does), then `index/all.json`, then `track-record.json`, then `digests.json`, then `manifest.json` last. A write failure stops the sequence (the old manifest stays; its age is the alarm), marks the Run `partial` with `failures:[{stage:'views'}]`, and leaves the facts as written.

**One title rule** (decision 0037 amendment, 2026-11-04): `titleOf` in `src/views.js` is the only place a story title is chosen: the headline of the story's newest non-article entry within the 30-day window (`WINDOW_DAYS`), else its newest entry overall. "Newest" is the last entry in one total order, `entryOrder` in `src/indexViews.js`, the same comparator `weekly.json` lists a day in: record date, then archive day, then the place in that archive day's list (`sourceRow.index`), then `at`, then eventId (so entries tied on date and `at` still have one answer). The story view's top-level `title`, the `title` of every `index/active.json` / `all.json` row, `index/web.json` `threads[id].title` and `links/*.json` `otherTitle` are that string (the web node summary only for a thread the record has no titled row for). `analysis.threadTitle` is a model paraphrase and stays an analysis field.

**Only changed views are written** (decision 0037 amendment, 2026-11-04; S3 PUT requests were about 70% of the AWS bill because every run rewrote about 9,000 files). `record/views/digests.json` is `{schemaVersion:1, builtAt, files:{"<path under views/>": "<md5 of the exact bytes written>"}}`. `src/digests.js` reads it once at the start of a publish; a missing, unreadable or malformed file is an empty map, so the first run after deploy (or after you delete the file) writes everything: log `digests: missing`. Each view is hashed as `JSON.stringify(obj without its top-level builtFrom) + "\n"` (the bytes `s3json.putLatest` writes, minus the stamp) and put only when its hash differs. **`builtFrom` is not part of the digest** (amendment 2026-11-05): `factsThrough` is the newest fact of the whole record, so it advances every day in every view, and hashing it made the 23:45 UTC run write all 9,293 files ("skipped 0 unchanged", 2026-11-04). An unchanged view keeps the stamp of the run that last changed it, which is honest: its content is a function of the facts, so a later fact that could alter it changes the digest and rewrites the view with the new stamp. The page's record-wide freshness is the manifest's (`builtAt`, `factsThrough`), written every run. The readers of a per-view stamp are `useNarrativeThread.combineTimeline` (the archive adds days after it, only on the not-fresh path) and the board's `StoryTree` ("Facts run to ..."); both then read "nothing for this story after this day". A daily run writes the views whose content changed (stories and links of the stories with new facts or a flipped provisional flag, the counts days it rebuilds, the indexes whose rows changed, `weekly.json`, `active.json`/`all.json`) plus `digests.json` and the manifest. The map is rebuilt from the views built in this run, so a story that no longer has a view drops out of it (its file stays in S3; nothing is deleted). `digests.json` goes just before `manifest.json`, which is written every run (its `builtAt` is the freshness the pages read), so a failed write leaves the old digests and the old manifest and the next run repeats the writes. Log line per run: `[views] wrote N of M files (skipped K unchanged), digests: read|missing` (N counts `digests.json` and the manifest); a refresh returns `written`, `viewsSkipped` and `digests` with the other publish numbers (not in the Run, whose schema is closed). A view deleted from S3 by hand is not restored while its digest matches: delete `digests.json` to force a full write. `builtFrom.provisionalThrough` is stamped only on a view that holds provisional content (a story with a provisional entry or fork, its `forecasts/` and `links/` file, a day's `counts/` file with provisional facts of that day, and `index/active`, `all`, `weekly`, `today`); every other view has `{factsThrough, readingsThrough}` only, so a refresh leaves it byte-identical. The reader's rule (`useNarrativeThread`: through = max of the two, the archive adds later days) stays right: a story without the stamp does not hold today's entries, so the archive supplies them. The manifest keeps the global `provisionalThrough`. A refresh whose provisional facts did not change therefore writes only `digests.json` and the manifest; the nightly run (no provisional facts) rewrites just the views that held provisional content. The first run after the 2026-11-05 digest change rewrites every view once (the stored digests were of the full body, stamp included). Preview on live data: `node dryrun-digests.mjs <liveDir> [--sample N]` (header of the file; nightly-style build only, since a refresh's provisional entries come from DynamoDB; the live bodies are hashed without `builtFrom`, as the publisher does).

Assignments (0040 rule 3): an entry belongs to the story of its current assignment, the one with the latest `at` (ties: operator, then review, then ingest, then larger `eventId`); an entry with no assignment fact stays on its archive thread. A reassigned entry leaves the old story's `entries`, row counts, `iso3`/`actorIds`/`sourceIds`, `counts/` `newEntries` and link grounds, and appears in the new story's, carrying `reassignedFrom` (the archive thread it left). Corrections follow their entry. With only ingest assignments the views are byte-identical to the views without any (golden test). An assignment may also name an `article` fact (recovered articles the operator links to a story): the article then appears in that story's `entries` as `{eventId, date, at, precision, title, summary (the snippet or null), sources:[{outlet, url}], kind:'article', recovered, recoveredFrom}` (entry rows carry no `kind`; the board's `StoryTree.jsx` reads only `eventId`, `date`, `title`, `summary` and `sources[].url/outlet`, so it shows an article row like an entry), counts in `entryCount`, `born` and `lastFactAt`, follows a merge like an entry (`fromThreadId`), and is counted in `counts/` as `articlesPlaced` (present only when nonzero), never as `newEntries`. An article with no assignment stays out of every story. An assignment naming neither an `entry` nor an `article` fact does nothing. `backend/record/cli/benchmark-assignments.mjs` builds such lines from the gap benchmark (see `backend/record/cli/README.md`).

`liveBranchCount` = branches of any `forecast_drawn` with `due >= today` and no verdict. `today` is the UTC day of the invocation. Rebuilds are idempotent: the same facts give the same bytes, except `builtAt` and `runId` in the manifest. Schemas and one example per view type: `schema/views/`. The IAM role needs `s3:PutObject` on `record/views/*` (shadow: `record/shadow/views/*`) before views can be written live; the live role (`newsStoryRecord-access`, read 2026-10-22) now includes `record/views/*`.

## Readings, merges and aliases in the build (step 3, BUILD node of the weekly loop)

The BUILD step of the weekly loop is drawn in [ARCHITECTURE_WEEKLY_REVIEW.md](../../../project-docs/architecture/ARCHITECTURE_WEEKLY_REVIEW.md) section 2; what this Lambda does with the inputs:

- Readings: `record/readings/YYYY-Www.jsonl` for every ISO week from the first facts day to today (no listing; a missing week is empty). Per `(threadId, subtype, key)` the latest non-superseded reading wins (key: `line` none, `chapter` `from`, `link` and `merge_proposal` `otherThreadId`, `alias` `canonical`); a reading whose `readingId` another reading names in `supersedes` is dropped; ties on the week go to the later `run`, then `readingId`. Malformed lines are skipped. `merge_proposal` and `alias` readings are not story content (aliases below).
- Aliases: `record/operator/aliases.json` (operator only; missing = none) maps variant actorIds to a canonical one; accepted alias readings (a Wikidata Q-number, no conflict) add to it, the operator file always wins. The map is applied to `actorIds` in story views, index rows and the links specificity count. Facts keep the ids they were written with.
- Merges and splits: see the fact table. A `story_split` cancels every `story_merged` of the same `(from, into)` dated at or before it; a merge dated after the split stands.

## Event

| Field | Meaning |
|---|---|
| `date` | the UTC day to process (default today) |
| `backfill: {from, to}` | replay those days oldest first through the same code; a day with no archive row gets a `missing` Run and no facts and does not throw |
| `refresh: true` | not a run (decision 0050): no fact, no Run, no `run` fact, no facts manifest write. Reads the facts, notes and readings as the nightly build does plus today's archive entries (`store.loadDay`: the `archive#DATE` row and the `today-archive` entries archived that day), makes each a `provisional` entry fact in memory (`provisionalEntryFact`), makes today's forecasts-inbox rows `provisional` `forecast_drawn` facts the same way, and rebuilds every view. Returns `{refresh, prefix, runId, today, entries, forecasts, unplacedForecasts, skipped, written, stories, active, provisional, provisionalForecasts}`; an entry or forecast that cannot become a fact, and a failed forecasts-inbox read, are in `skipped` (`what: 'entry'|'forecast'|'forecasts'`), not an error; a failed view write throws |
| `assignmentsBackfill: true` | one-time job: every `entry` fact already written gets its ingest assignment (below, Choices); not a nightly run |
| `shadow` | default `true`: every key moves under `record/shadow/` (`record/shadow/facts/`, `record/shadow/runs/`, `record/shadow/facts/manifest.json`); the flip is a prefix change |

### Refresh (decisions [0050](../../../project-docs/decisions/0050-fresh-views-after-ingest.md), [0052](../../../project-docs/decisions/0052-forecasts-inbox.md))

The agent rewrites today's archive during the day, so a refresh never appends a fact: today's archive entries, and today's rows of the forecasts inbox (`record/inbox/forecasts/<today>.jsonl`, shadow `record/shadow/inbox/forecasts/`), enter the views as **provisional** `entry` and `forecast_drawn` facts made in memory (`provisionalEntryFact`, `forecastFactsFor`), and the nightly run, which appends the real facts, replaces them. A forecast row takes the row's own `threadId`, else the thread of its topic among today's entries, with no window fallback; a row neither places is no fact (`unplacedForecasts`). A forecast's `eventId` is sha1(`forecast_drawn` + sourceKey) with sourceKey the row key `PRED#<topic>|<day>`, the same from the log and the inbox, so the nightly fact replaces the provisional one even after a later reconcile moved the row. A refresh never reads the PredictionLog, whatever `FORECASTS_SOURCE` says; a failed inbox read is in `skipped` and the entries still publish. Views stay a pure function of (facts, notes, readings, provisional facts): `buildViews(facts, {provisional})` drops a provisional fact whose `eventId` is already a fact, so a refresh after the nightly run changes nothing. Marks: `provisional: true` on a story entry row and on a fork; `provisionalThrough` in the `builtFrom` of every view and in the manifest only when there are some, with `provisionalEntries` and `provisionalForecasts` in the manifest (each only when nonzero); `factsThrough` stays the newest day of the real facts. `track-record.json` is built from the real facts only. A refresh takes about as long as the nightly build (13 to 17 s live).

## Rules the code implements
The reasoning is in the decisions: facts and their format [0036](../../../project-docs/decisions/0036-facts-file-format.md), views [0037](../../../project-docs/decisions/0037-views-from-facts.md), forecast loop [0038](../../../project-docs/decisions/0038-forecast-loop.md), raw before model and assignments [0040](../../../project-docs/decisions/0040-raw-before-model.md), notes [0042](../../../project-docs/decisions/0042-notes-move-to-the-record.md), question draws and track record [0043](../../../project-docs/decisions/0043-question-draws-in-the-record.md)/[0044](../../../project-docs/decisions/0044-track-record-view.md), fresh views [0050](../../../project-docs/decisions/0050-fresh-views-after-ingest.md), entries and forecasts inboxes [0051](../../../project-docs/decisions/0051-entries-inbox-and-today-view.md)/[0052](../../../project-docs/decisions/0052-forecasts-inbox.md). Behaviour kept here because the code is its only other statement:

Facts and Runs
- A day with no archive row and no today-archive entries ends its Run `failed` with `archiveDay:"missing"` and zero facts; a daily run throws after writing the Run, a backfill does not. `strict` (default `true`): a run throws after writing its Run when any day in its range except today ends `missing`; only an explicit historical replay passes `strict:false`. A backfill's `run` fact is dated the end of the replayed day.
- Entry `summary` is null (the archive row has none). A title-basis entry id uses the archive day, not the fact day, so a re-run keeps it. The Run's `runId` suffix is the attempt number counted from the existing Run object for the date; it also carries `date` and `daysWritten`.
- Entry time: a `publishedAt` is valid when it parses, is not after the entry's `archivedAt` (end of the archive day when absent) and is at most 30 days (`MAX_PUBLISHED_AGE_DAYS`) before the archive day; invalid sources are skipped. An exact `at` can fall on an earlier UTC day than the archive day, so that fact lands in the earlier day's file. Rows without `publishedAt` stay `precision: day`.
- One lookback: `LOOKBACK_DAYS` is 100, for the qid map and the dedupe of known facts (a forecast is due 7-90 days out and judged up to 3 days after). Inbox window: each run reads the run day and the 6 days before (a missing day is empty), keyed by decision day UTC; the event `{inboxFrom:'YYYY-MM-DD'}` reads from that day instead. A line becomes a fact each time it is read and is dropped as known when its `eventId` is in the 100-day facts; the views ignore a repeated `eventId`.
- A malformed inbox line is a failure of its kind on the Run (`partial`) and the rest is kept; an unreadable day file is a failure with `ref` = the day.
- Recovery hook only: an event `{recovery:true}` puts `recovery` in the Run's `notes` and refuses `forecast_drawn` for that day.

Verdicts (inbox only; no DynamoDB verdict query)
- The inbox line is the resolver's: `{schemaVersion:1, qid, threadId, branchId, forkId, result, voidReason, decidedAt, decidedBy, evidence:{quote,url,title,date}|null, reason, revision, sourceKey}`. A `record gap` void also has `gapDays`, copied to the verdict fact; the track-record view counts such voids in `counts.voidRecordGap` (decision 0055). The shadow prefix reads `record/shadow/inbox/verdicts/`.
- "Resolvable" is `question === true` and a non-empty `qid` (`isResolvable` in `src/facts.js`). A branch that is not resolvable is legacy: `legacy: true` on its story-view branch, counted in `branchCount` but not `liveBranchCount` and in no day's `branchesDue`.
- Legacy void job: event `{legacyVoid:true, shadow:true|false}` (shadow default true) appends one `issued_before_method` void verdict per legacy branch to the facts day of the job time (`sourceKey = legacy-void|<branchId>`, so a re-run appends nothing), registers the day and rebuilds the views; no Run object. Run live once on 2026-10-30. The story-view verdict is `{at, result, decidedBy, evidence, voidReason}`.

Articles and assignments
- Raw articles are `article` facts; an entry's `eventId` stays url-only. An article's `at` is `publishedAt` only when it parses and is not after `fetchedAt`, else the start of the fetch day with `precision: day` (no 30-day floor, so a recovered article keeps its real publish day); `counts.articles` counts by the fact's date. The article inbox is read before the missing-archive check, so `inputs.rawDay` (`missing`, `{thin: n}` under 50 lines, `present`, or `null` when unreadable) is recorded even for a missing archive day; article, verdict, merge and split facts are appended whenever their inbox has lines, only entry, `story_born` and `forecast_drawn` depend on the archive.
- Ingest assignments are written only for a fresh entry fact that has an archive thread, so one article is one fact and the first thread claims it; reassigning is the operator's or the review's act. Inbox assignment lines need `at` (the latest `at` decides and is part of the `eventId`); `by:'ingest'` is refused in the inbox. `supersedes` is stored and used nowhere. An emptied story stays a story (empty `entries`, null `lastFactAt` when nothing is left); assignment facts never bump `lastFactAt`; a reassignment onto a merged-away story lands on the survivor, tagged `fromThreadId`. A reading of subtype `assignment` is skipped here: it changes nothing until the operator writes the inbox line.
- `assignmentsBackfill` derives one ingest assignment per existing `entry` fact (skipping ids already present), registers the days, rebuilds the views and returns `{assignmentsBackfill, prefix, entries, written, alreadyAssigned, days}`; `producer.runId` is `assignments-backfill-DATE`. It has not been run; until it is, an entry without an assignment stays on its archive thread.

Views
- Both index files are `{schemaVersion, builtFrom, stories:[row]}`. `builtFrom.factsThrough` and the manifest's = the latest `date` of any fact except `run`. Active window: a story whose newest fact `date` is within today and the 59 days before.
- A story's `lastFactAt`, `born` (earliest of its `story_born` and entries), `title` (first entry by `date`, `at`, `eventId`) and counts cover its own facts plus the entries merged into it. Only entries (and corrections of them) move from a merged story; its `forecast_drawn`, `verdict` and `story_merged` facts stay with it. A merged story's row in `all.json` keeps `threadId, born, lastFactAt, title, aliasOf` and empty counts; `counts` attribute its days to the survivor for all days. A branch's `verdict` is the newest verdict fact for its `branchId` (by `at`, then revision); any result ends it being live. A repeated `eventId` keeps the earliest by `at`; facts are read in `(at, eventId)` order.
- Links rule (0037 amendment 2026-10-22): grounds are actors and countries only, each counted only if fewer than 5% of the active stories carry it (`SPECIFIC_SHARE`; with fewer than 41 active stories no shared id can be specific and every links file is empty); both stories' `lastFactAt` at most 14 days apart (`LINK_WINDOW_DAYS`, gap in `daysApart`). `sharedActorIds` and `sharedIso3` list only the specific ids, `sharedSourceIds` every shared source. Sort by the rarest shared specific id, then `otherThreadId`; cap 50. Every story has a `links/` file: an empty one for a merged or idle story, so an old file is overwritten rather than left stale.
- `entriesOmitted` is always present (0 when nothing was cut). Entries carry `fromThreadId` only when merged in, and `corrected: true` only when a correction names them.
- Readings in the build: the readings, the merge and split inboxes and the operator alias file all follow the run's prefix (a shadow run reads `record/shadow/...`). `builtFrom.readingsThrough` and the manifest's are ISO week labels, the newest week among the readings used, null with none; weeks before the week of the first fact day are not read. A chapter's reading key is its `from`, so a re-read chapter with a changed span must name the old one in `supersedes`, otherwise both stand. `reading` is `{state:"read", week}` when the story has a line, chapter, branch-status or link reading. A merged story's own readings are not shown; a confirmed link to a merged story points at the survivor and a link to itself is dropped; `confirmedLinks` are shown on the story the reading names, not mirrored, and exist only in `links/` files. `story_split` payload is `{from, into, reason}` with the time in the envelope `at`. A malformed merge or split line is a `merge` or `split` failure (Run `partial`).
- Alias conflicts: a reading is rejected as a whole when a variant is already mapped to a different canonical, its canonical is itself a variant, or a variant is another entry's canonical; among readings and inside the operator file the earlier entry wins; a malformed operator file fails the views stage (Run `partial`). A canonical id in the views is `wd:Q...` when the alias entry carries a `wikidataId` (two entries with one Q-number pool into one id), else its `canonical` name. `generic:true` on an operator entry (`{canonical:'name:protesters', variants:[...], generic:true}`) marks a crowd or "the government": it never takes a `wd:` id, still appears in `actorIds`, and is never a ground in `links`. Facts keep the ids they were written with.
