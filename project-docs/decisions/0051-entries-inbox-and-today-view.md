# 0051. New entries reach the record through an inbox, and the pages that read DynamoDB for "today" read a record view

Status: accepted (operator, 2026-10-31, step 5 build B2); follows 0035, 0036, 0042, 0046, 0047, 0050. Built and proven locally; nothing is deployed, no env is set, no object is written. The coordinator deploys, backfills the inbox shadow first, and sets the env (hand-off below).
Date: 2026-10-31

## Context
Step 5 retires the DynamoDB world tables. NewsCache `archive#DAY` and `today-archive` are still the only source of the day's entries for the facts run (`store.js`, `world.archiveRange` / `archiveDay`, day-zero rule) and for the refresh of 0050, and five live actions still answer "today" to the pages:
`topics` (NewsCache `latest`; `useGeminiTopics` on `/`, `/today`, the board), `today` (`today-archive`; `/today`), `summary` / `prediction` / `trace_cause` (SummarizeAndPredict `TOPIC#`; `/today` cards and the map's story card).
The record has the entry facts a night late, and not what `latest` holds.

Verified in the code and on live data (2026-10-31):
- The agent writes `archive#DAY` (10 sources) and `today-archive` (3 sources, 24 h) in `buildAndWriteArchive`. In both, an entry of a topic seen again **replaces** the earlier one, moves to the end of the list and carries the thread id that run assigned (`assignThreadId` joins an earlier generation of the same day, so it is usually, not always, the same thread). The row is capped at the last 50. `archivedAt` is read from the clock separately for each copy, so an entry's `archivedAt` differs by a few hundred milliseconds between the two items.
- The entry fact reads: date, `archivedAt`, sources (`source`, `url`, `title`, `snippet`, `tier`, `publishedAt`), `title`, `threadId`, `iso3`, `actors`, `regions`, `category`, `eventType`, `continuesTopic`, `topicId`, and the row's provenance (`sourceKey` = `archive#DAY|<generationId>|<topicId>`, `sourceRow` with the entry's position in the row). Never `ai`.
- `latest` is the staging item copied to `active`. An archive entry lacks what only the raw topic has: `urgency`, `urgencyReason`, `significance`, `x_trending`, `primaryCountry`, `mentionedCountries`, and the run's identity (`generationId`, `updatedAt`, `model`, `limit`, `generatedDate`) and order. The pages use `x_trending` (trending tag and count), `urgency === 'high'` (urgent tag, the lede's score) and `primaryCountry` (cards, the lede, the map's story card and feed); nothing reads `significance`, `urgencyReason` or `mentionedCountries` (`newsBreakingAlert` reads `significance` server side; out of scope). A source's `age` ("1 hour ago", shown by `Home.jsx` beside each source) and `enrichScore` are on the archive entry's source objects already, so they need nothing new.
- All six topics of the live `latest` (generation `gen-1793420169805`) were also in `today-archive`, with the same topic and thread ids.
- None of the five actions checks membership (`newsSensitiveData` `resolveTier` is used only by `country_history` and `corrections_feed`). The `summary` family returns the full text; the archive's `ai` is cut at 1,500 characters.

## Decision

### 1. The entries inbox
- **Object.** `record/inbox/entries/YYYY-MM-DD.jsonl` (shadow: `record/shadow/inbox/entries/`), day = the UTC date of the archive row (`formatDateKey(now)`). One writer: `NewsProjectInvokeAgentLambda`, appending after its archive write, on the same footing as the entry notes: gated by env `ENTRIES_INBOX_PREFIX` (unset = nothing is written; the coordinator sets `record/shadow/`, then `record/`), best-effort (a failure is logged as `[inbox]` and never fails the run; the DynamoDB writes stay).
- **Line.** The entry exactly as the daily row stores it (after `trimAi`, up to 10 sources: topicId, threadId as assigned, title, category, regions, search_keywords, iso3, actors, event_type, sources with `publishedAt` / `outlet`, `archivedAt`, `generationId`, `ai`, `continues_topic`) plus `inboxId` (`batch|n`, the append key), `batch` (the archive write's ISO time, shared by the run's lines; also the `today-archive` item's `updatedAt`), `n`, `latest` (the fields above that only `latest` holds, for this topic) and `run` (`of` = topics in the staging item, `model`, `limit`, `updatedAt`, `generatedDate`, `generatedYear`, `generationId`).
- **Replacement rule.** The agent's own merge, now one function (`backend/shared/src/entriesInbox.js` `mergeArchiveDay`, used by the agent for both rows and by the replay): per batch in file order, `list = [...list.filter(topic not in batch), ...batch]`, last 50. Replaying a day's lines therefore gives exactly the entries `archive#DAY` ends the day as, **in the same order** (so each entry's position in the row, which is in its provenance, is reproduced). "The last line per topic wins" is the consequence, not the implementation: the position of a replaced topic is the end of its replacing batch.
- **Reading.** `newsStoryRecord` env `ENTRIES_SOURCE` = `archive` (default, unchanged) | `inbox` | `compare`. `inbox` reads the 30-day window and the refresh's today from the inbox through `world.archiveDayOfEntries`, which returns the same normalised entries as `archiveDay` (same provenance), so `entryFact`, `birthByThread`, `threadOfTopic` and the provisional entries are unchanged code. A day with no file is a missing day. `compare` builds both, **uses the archive**, and logs `[entries-compare]` with per-day counts, topics on one side only, and the fields that differ (console.warn when any); it writes no inbox-derived fact. Not reproduced by the inbox: entries the `today-archive` item adds to today's day row (day-zero rule), which exist only when the daily write failed or the 50-cap dropped them; `compare` shows them.
- **Backfill.** `backend/record/cli/build-entries-inbox.mjs` builds the inbox files for the last N days from the archive rows into local files (one batch per run, in the row's order) and proves equality with `entryFact` (below). The same files, uploaded once to `record/shadow/inbox/entries/`, then `record/inbox/entries/`, are the 30-day start, so `inbox` mode has a full window before the agent has written 30 days of its own.

### 2. The today view
- **Object.** `record/views/index/today.json` (schema `backend/record/newsStoryRecord/schema/views/today-index.schema.json`, example beside it), built by `todayView.js` inside `buildViews` for **both** nightly and refresh runs from the inbox lines of the last two UTC days and the entry notes (0042). Written with the other index views (cap 2 MB, the build fails over it); **absent while the inbox has no line**, so a page falls back to its action until the agent has written one. The inbox is read whatever `ENTRIES_SOURCE` says; the view needs the lines, not the facts: the entry fact has neither `latest`'s fields nor the order and replacement rule of the 24 h list, and the lines carry both. Entry notes supply the full model text.
- **Shape.** `{schemaVersion, builtFrom, updatedAt, latest, entries}`. `entries` = what the `today-archive` item holds after the newest write (the same merge across midnight, the 24 h rule against each write, the last 50), in its order, each the archive entry plus `eventId`; `latest` = `{batch, generationId, model, limit, updatedAt, generatedDate, generatedYear, topicIds}` for the newest run **only when that run's lines are all there** (`run.of` = line count) and null otherwise (an older agent, a single-topic manual run), and the entries of that run carry `latest` (urgency, x_trending, primaryCountry...) and `notes` (`{summary, prediction, trace_cause}`: the latest entry note per part, the exact note over an archive copy, `{format, content, at, model}`).
- **Mappers.** `frontend/src/shared/api/todayView.js`: pure `topicsPayload(view, now)`, `todayPayload(view, now)` (24 h cut at read time, three sources), `notePayload(view, topicId, kind)`, each returning the action's envelope or null when the view cannot answer. `contentService` asks `viewFirst`: the view while the manifest is fresh (`viewsFresh.js`, 0050) and the mapper answers; otherwise the action, as before. A view that cannot be read is reported (`today-view`) and falls back. Nothing else in the pages changed: `useGeminiTopics`, `useTodayArchive`, `Home.jsx`, `useStoryCardData`, the board's topics all keep calling `contentService`.
- **Membership.** The view holds only fields the five anonymous actions already return. It carries no drift depth, no corrections, no member field; `summary` / `prediction` / `trace_cause` text is public today.

## Consequences
- The facts run, the refresh, and the pages' "today" can run with no read of NewsCache `archive#`, `today-archive` or `latest`, and no read of `TOPIC#`, once `ENTRIES_SOURCE=inbox` and the hooks are served from the view. The DynamoDB rows are still written (the other readers, listed below, still need them).
- Home loses nothing: the selection and its order, `urgency`, `x_trending`, `primaryCountry`, the run's `updatedAt` (the "as of" label and the poll for new data), `generatedDate`, `model`, the 13-topic limit, and the 24 h list with its AI text come from the view. The only field of the `topics` item not rebuilt is `activatedAt` (no page reads it); the topics payload even keeps `significance`, `urgencyReason`, `mentionedCountries` and each source's `age` and `enrichScore`, so it equals the item field for field.
- Differences from the actions, measured on the live capture of 2026-10-31 09:47 UTC (the fixtures of `frontend/src/shared/api/__tests__/`): `topics` equal field for field (6 of 6 topics, same order, same run fields except `activatedAt`); `today` equal for 12 of 12 compared entries and `updatedAt` except the entry's `archivedAt` (the daily-row copy is later by under a second, two clock reads); `summary` / `prediction` / `trace_cause` equal text, model, time, generation, thread, title and format for the 6 topics of the run; a JSON note is returned re-serialised (`JSON.stringify` of the parsed note, the same value as the stored string with other whitespace; the pages parse it); the fields `latencyMs`, `lastVerifiedAt`, `provider`, `sourceFingerprint`, `remainingTtlSeconds`, `promptVersion` are not in the view (no page reads them: `Home.jsx` stores `remainingTtlSeconds` in metadata it never displays); a part the action has none of (3 of 6 predictions that day: `Cache miss`) is null in the view too, so the page asks the action and gets the same miss.
- The view is rebuilt after every ingest (refresh at +10 min, 0050), so pages see a run within about the same 15 to 25 minutes as the other views; the 9-hour manifest rule decides when the actions take over again.
- Size: 235,777 bytes for the 33 entries built on 2026-10-31 (21 inside 24 h at read time; the full set is kept so the page's own cut is exact), 12% of the 2 MB cap. The model text is only carried for the latest run, so the file does not grow with the 50-entry cap beyond the trimmed `ai` of each entry.
- `compare` plus the CLI make the switch to `inbox` a measured one: the equality proof first, then a shadow day of `[entries-compare]` lines with zero differences, then the flip.

## Equality proof (read-only, 2026-10-31)
`build-entries-inbox.mjs --days 30` against live NewsCache: 25 archive days exist in the window (5 missing, as in the archive path), 838 entries, 838 entry facts compared, 2,064,281 bytes of fact JSON identical (including `sourceKey`, `sourceRow`, position), story births and thread-of-topic identical, no day-zero extras, and the provisional facts of the refresh for 2026-10-31 (6 entries) identical. Replacement rule: a seeded multi-run property test (`backend/shared/test/entriesInbox.test.js`) keeps the shared merge equal to the agent's former inline merge for both rows and equal to the replay for days over the 50 cap.

## Out of scope (unchanged, listed so they are not forgotten)
Other readers of `latest` / `today-archive`: the `rss` action, `newsPostDevTo`, `newsPostLinkedin`, `newsBreakingAlert`, `newsRecommend`, `newsBoard` presets and connect (`world.latestTopics`), the Worker's bot pre-render (`topics`); the agent's `staging` and `seen-today` working rows; the forecasts inbox (B3); `archive_range` for the countries list and the story timeline's `narrative_thread` fallback; the DynamoDB deletions themselves (step 5, one yes each).
