# Security review, 2026-11

Scope: every Lambda handler and frontend call that takes user input or a token, the front Worker, `index.html` and what `docs/config.js` exposes. Read-only. Source: `origin/main` at `db3d7d96`, code and in-repo docs only. No AWS call, no network probe of a live endpoint, no code changed. Facts come from the code; anything that depends on live AWS, Firebase or Cloudflare state is marked "needs live check" and listed in section 4. Overall: the per-user paths are sound in structure. The caller's uid comes from the verified token and never from the body (`newsSavedItems` index.js:259, `newsRecommend` :371, `newsBoard` :217, `newsSharedAnalysis` :107/:85), keys are built from fixed prefixes, the share path sanitises every string and URL, the frontend renders text through React and a safe Markdown subset, email HTML goes through `escapeHtml`, and the Polar webhook verifies an HMAC with a 5 minute window before any write and fails closed with no secret. The weak points are: a fail-open identity check when `FIREBASE_PROJECT_ID` is unset (F01), no security headers on the production Worker (F02), three unauthenticated or cheap-to-abuse surfaces with no rate limit (F03, F04, F05), anonymous Firebase accounts that defeat per-user limits (F06), server-side fetches of third-party URLs (F07, F09), third-party text reaching an LLM and then readers with no human gate on some paths (F08), and plaintext secrets with a shared, broad role (F11, live check).

Testing-round leads used: coverage-report.md auth notes (FIREBASE_PROJECT_ID, newsClientErrors, CORS rule), pr-t-readapi-auth.md items 1 to 6, pr-t-proxy.md items 1 to 4. The invalid-JSON 502 in `newsSensitiveData` is already fixed on main (index.js:119-123). Lead 2 (a lapsed member cannot unfollow, index.js:415-417) is a product call, not a vulnerability.
