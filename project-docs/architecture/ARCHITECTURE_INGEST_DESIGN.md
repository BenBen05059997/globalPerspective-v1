## Vocabulary and ownership

A topic is one editorial selection; a story is an editorial thread (`threadId`); a cluster is a grouping of classified headlines; a situation is a map pin. Existing wire fields `storyId` and S3 `stories/` are legacy cluster names, not another meaning of story. Rename internal variables first; compatibility readers/writers keep legacy wire names until migration is verified.

Follow the coordinator's adopted ARCHITECTURE_TIMELINE.md: newsStoryRecord writes the facts (`record/facts/YYYY-MM-DD.jsonl`), the planned newsRecordReview writes the weekly readings (`record/readings/`), and the views are rebuilt from both. Existing producers remain raw-source writers for now. The agent supplies source rows for `entry`; it must not start a second timeline writer. Consumers read views, or the shared `backend/shared/src/world/` reader until the relevant view exists. A `situation` kind does not exist yet: it is deferred (ARCHITECTURE_TIMELINE §3), as are coverage events (coverage is Run data, not a fact). Repairing an already published entry needs an appended `correction` referencing its eventId; never rewrite the old fact.

Lane D owns only agent threading/guard and CLI code. Situations, shared readers, monitoring, schedules/IAM, worker/frontend, timeline schema and repository architecture docs are coordinator work. Neither option changes the user-side DynamoDB stores as part of ingest restructuring.

```json
{"ID":"expire-inactive-cluster-state","Status":"Enabled","Filter":{"Prefix":"stories/state/"},"Expiration":{"Days":7}}
```

### Preferred duplicate repair: aliases and correction events

For the18 duplicate event groups, keep historical archive entries, PRED snapshots, THREAD_HISTORY and timeline events unchanged. A **whole clean story merge** is an alias row mapping source thread to canonical destination, backed by an appended `correction` event. Proposed representation: a materialized alias view such as `record/thread-aliases/latest.json`, built only by newsStoryRecord from the correction timeline; each alias row records from/to, effectiveAt, correctionEventId and repairId. This exact new view path/schema needs coordinator agreement and docs/IAM integration; it is not present or written by lane D. A DynamoDB compatibility alias can be considered only with a designated single writer and the same correction provenance; do not create two authoritative alias registries.

Use the already approved `correction` kind, not an invented merge event kind. A versioned payload can carry operation `thread_alias`, from/to, evidence source keys, reason and immutable repairId. Its sourceKey must identify the repair decision, not the execution timestamp, so repeated application appends no duplicate event. Correction eventId follows the shared record rule. The alias view detects cycles, existing conflicting aliases and destination ambiguity; a reversal is a new correction superseding the old decision, never deletion of the old event. Resolve transitively with a bounded chain and explicit error on a cycle.

A **mixed source** cannot get a whole-thread alias. The member lists in CLEANUP.md define entry-scoped reassignment corrections, with sourceEntryKey, fromThreadId, toThreadId and evidence. Fold those into current story views; unrelated members and the old story remain. Membership corrections must carry both observation identity and raw source provenance so the same observation found in rolling and dated stores is handled once. Story birth is a persisted historical fact; a correction may change a current view's canonical membership but must not invent a new birth on repair day.

Shared/world and consumer views must resolve canonical ids before grouping/forecast lookup, while retaining originalThreadId in provenance and keeping as-of historical interpretations available. Current PRED lookup deliberately rejects rows naming a different thread, so alias awareness must be added there before old PRED rows become reachable under a new canonical id. Do not rewrite forecasts to make that query work. Verify old story links, board pins/pair caches, map focus aliases and current analyses. Published weekly content remains historical; future/corrected views can link a correction. Raw CLI merge/move/split is consequently a legacy pre-timeline repair mechanism, not the preferred18-event execution plan. CLEANUP now states that prominently.

### Stable entry identity and the shared sourceKey contract

Choose **observation identity `(generationId, topicId)`** for new producer entries. `topicId=title-rank` alone is unstable across runs; the same title at rank4 tomorrow is not today's observation. The tuple is stable for retrying the same selector generation and distinguishes genuinely different generations, including a developing event under a repeated topicId. Persist an entryKey using an unambiguous canonical tuple encoding, e.g. a versioned hash of JSON `[generationId,topicId]`; do not hash a title or relative age alone. The agent should retain it when copying to latest/rolling/dated archives; a retry must never create a new key from collection time. This field addition is a coordinator proposal, not another lane D producer change in this follow-up.

**Keep world/'s existing provenance sourceKey exactly as implemented**, not a new parser around it: `<archive#date|today-archive>|<generationId or archivedAt>|<topicId>`, plus sourceRow `{store,key,index}` with the original unfiltered index. These are source-occurrence identities, intentionally distinct for rolling versus dated storage. Timeline `eventId=sha1(kind + sourceKey)` remains compatible with41b71786. The record ingestion policy needs an explicit occurrence-to-observation mapping to avoid double-counting rolling/dated copies; do not silently drop the archive prefix from sourceKey or change an existing eventId. Conflicting payloads for the same observation key must be reported and retained for review, not arbitrarily overwritten.

Where generationId is absent, world/ falls back to archivedAt for provenance; mark observation identity/first-observation time approximate and retain the raw source key. Neither threadId nor raw array index belongs in the producer observation key: membership may be corrected and raw arrays can be filtered/reordered. Raw index is still required provenance. Content keys based on normalized article ids/time/action can later link two different observations of one event, but must remain a separate event/cluster identity and must not collapse a legitimate development just because it reuses an article URL.

The14 stale Oct20 rows have the same `(gen-1792440950003,topicId)` as14 Oct19 observations. CLEANUP enumerates exact source keys and retained counterparts: exclude invalid duplicates before first capture, or append corrections if captured already; no raw deletion and no rewritten timeline lines. The other5 repeats in the coordinator's19/176 count need their own evidence. Expiring sources must be captured promptly: rolling archive24h; thread history/drift60d; dated archive, analysis and country history90d; only DRIFTLOG is permanent under the audited contracts. The reader's provenance and persisted `story_born`/coverage cursors must survive that expiration.

### No data is not a situation ending

Observed map failure: ingest saw classification drop417→124 and clusters80→55 during provider failure but still returned ok:true. Cached hits are available observations, not proof that omitted news disappeared. The tracker then closed situations from the missing clusters; emitting those as `situation closed` facts would corrupt the timeline. Fix this in both architecture options before accepting map events into the timeline.

The ingest run manifest must distinguish `complete`, `partial` and `failed`, with fetched/eligible/cached/classified/unclassified/deferred counts, per-feed or country coverage, batch errors, source-observed timestamps and lastCompleteRunId. An empty result needs a reason. All-classification cache hits may be healthy if fetch/coverage is complete; zero fresh LLM calls alone is not an ingest failure. A402, fetch outage, batch cap backlog or parse failure must not advance a complete-coverage watermark. Preserve unclassified article ids/snippets in the durable backlog for retry; do not silently discard them. Publish current positive observations separately from the latest complete snapshot.

On partial/failed/stale news coverage, the tracker may fold sufficiently supported positive observations but **must not increment disappearance/cooling/closure counters from absence** in uncovered input. Conservative first implementation: freeze all news absence-driven transitions for any incomplete news run. Later, permit country/feed-specific freezing only when coverage boundaries are trustworthy. Keep prior news situations visible with a lastKnownAt and an explicit unavailable/stale coverage status; sweep time is not observation freshness. Do not emit a closed/ended situation event, or refresh lastSeen, just because no classification arrived. Healthy independent GDACS can continue its own lifecycle; a GDACS outage needs its own absence gate.

An absence-driven closure requires fresh complete coverage spanning the relevant event window and the configured consecutive-check/cooldown threshold; a positive sourced closure can be recorded separately. Do not count several30-min sweeps of the same complete ingest run as independent new evidence of absence: persist the last counted ingestRunId and source watermark. Recovery resumes normal counters only from new complete runs, reconciles aliases and invalid closures through corrections, and never backfills missing days with fabricated observations. A `coverage` fact can record the outage using the approved kind; it must not masquerade as a `situation` transition. Test402 with cached hits, total fetch failure, capped/deferred batches, healthy empty feed coverage, repeated same-run sweeps, independent GDACS success, and recovery.
