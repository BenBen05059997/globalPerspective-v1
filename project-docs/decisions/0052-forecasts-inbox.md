Status: accepted (operator, 2026-10-31, step 5 build B3); follows 0035, 0038, 0043, 0044, 0045, 0050, 0051. Built and proven locally 2026-10-31, deployed 2026-11-01: the inbox, the views, the readers and the snapshot retirement are live (see Consequences and "Retired and not retired"); the hand-off below is the order it was done in.
Date: 2026-10-31

## Context
Step 5 retires the `PRED#` rows of the PredictionLog (the commitment state stays, below). `PRED#` still has four readers besides the pages:
- `newsStoryRecord` scans the 30-day window of `PRED#` rows (`world.scenarios`, `store.js`) to write `forecast_drawn` facts (policy statement `PredictionLogScan`).
- `newsPredictionResolver` scans `PRED#` rows with a question schema twice: the questions issued in a week (the draw's pool) and every open question branch (the nightly watch).
- `newsPredictionsSnapshot` scans the whole log every 30 minutes into `predictions/track_record.json`, which the `prediction_track_record` action serves and the freshness monitor's settle alarm reads (`settleHealth`).
- `prediction_snapshot` answers three pages live (the briefing's next question, the country card's deadlines, the analysis context) and the story page's fallback.

Measured on 2026-10-31: 7,114 items in the log; 669 `PRED#` rows in the last 30 days, 4,848 question branches in them; no row has ever been moved by the thread reconcile (`drawnThreadId` is on none of the 7,114).

## Decision

### 1. The forecasts inbox
- **Object.** `record/inbox/forecasts/YYYY-MM-DD.jsonl` (shadow `record/shadow/inbox/forecasts/`), day = the row's SK (the UTC day the forecast was drawn). One writer: `NewsProjectInvokeAgentLambda`, gated by env `FORECASTS_INBOX_PREFIX` (unset = nothing is written; the coordinator sets `record/shadow/`, then `record/`), best-effort (a failure is logged as `[inbox]` and never fails the run; the DynamoDB writes stay). The lines of a run are queued as the DynamoDB writes succeed and appended once, after the reconcile, by `inboxId`.
- **Lines** (`backend/shared/src/forecastsInbox.js`, the one place that knows the format):
  - `drawn`: `{type, inboxId: 'PRED#<topic>|<day>|drawn', day, row}`, `row` = the item exactly as the agent put it (put-once: a topic's second forecast of the day writes no line).
  - `thread`: `{type, inboxId: '<PK>|<SK>|thread|<at>', day, PK, SK, threadId, was, at}`, one for each reconcile update (`SET threadId = :t, drawnThreadId = if_not_exists(drawnThreadId, :old)`), written only when the update succeeded.
- **Last-wins rule.** Replay in file order: the first `drawn` line of a key is the row; each later `thread` line sets `threadId` and, if the row has none, `drawnThreadId = was`. A `thread` line with no `drawn` line is an orphan (counted and logged, not applied). Replaying a day gives exactly the rows the log holds for it.
- **Why the whole row.** The facts, the resolver and the snapshot need different fields of it, and a row is 2.8 KB; a lean line would need a new format for each reader.

### 2. `newsStoryRecord` reads it (`FORECASTS_SOURCE`)
`log` (default, unchanged) | `inbox` (the 30-day window from the day files through `world.snapshotsOfRows`, the same filter, mapping and order `world.scenarios` has, so provenance and `forecastFact` are unchanged code) | `compare` (both are read, the **log** is used, differences are logged as `[forecasts-compare]`, a warning when there is one; the inbox's first day marks where it starts, earlier days are skipped, not different). `inbox` mode reads no PredictionLog table; `PredictionLogScan` can then be removed from `newsStoryRecord-role`. The forecast facts of a nightly run are built by one function (`forecastFactsFor`), which the proof CLI uses too.

### 3. The resolver finds its questions in the facts (`QUESTIONS_SOURCE`)
`log` (default) | `record` | `compare`. `record` reads the `forecast_drawn` facts of `record/facts/` (the week's days plus one, for a forecast drawn after midnight; 120 days for the watch) and turns each fact back into the row fields the rules read (`rowOfFact`), so `lib.eligibleQuestions` and `watch.questionsFromPreds` run on both. The pool and draw rules moved to `backend/shared/src/questionPool.js` (the resolver's `lib` re-exports them; the record's view uses the same code). A week is drawn only when each of its days has a facts Run `ok` or `partial` (a missed night postpones the draw to the next tick, reported in the tick's errors) so the pool cannot be smaller than the log's. `compare` serves the log and logs `[questions-compare]`. The story title is not on the fact; it is the topic id without its `-<n>` suffix (669 of 669 rows).

### 4. The track-record view carries what the snapshot job carried
- **`draw`** on each of the last four drawn weeks: `{K, pool: [{q, c}], picked: [{qid, h, clusterKey}]}`, the pool rebuilt from the week's forecast facts by `questionPool.poolOfDraw` and published **only when it reproduces the draw** (size = the draw's `eligible`, and the rule with the revealed seed gives the same picks with the same hashes and keys), under the current lead window (7-90) or the one before 0045 (7-84). The page's "Verify this draw" uses it; the action is the fallback for a week with none. W41's draw is not reproducible: one pick's story thread changed after the draw, so its cluster key no longer matches (qids and hashes do), and the view publishes no `draw` for it (it leaves the last four drawn weeks with W45's draw on 2026-11-09 anyway).
- **`settleHealth`** on `questions`: `{expectedDrawWeek, drawMissed, commitMissing, lastVerdictAt, dueUnsettled, oldestDueUnsettledDays}` from the commit, draw, sampled and verdict facts, as of the build. It equals the old board's on the parity grid of `trackRecord.test.js` (five dates) except for the tick.
- **The tick** is not a fact. The resolver writes a heartbeat `{at, ...}` to `SETTLE_HEARTBEAT_KEY` (`record/views/health/settle-tick.json`, served under `/data/record/views/` like the views) at the end of a non-dry tick; off while the key is unset; best-effort.
- **The monitor** (`SETTLE_SOURCE=record`; default `action`) reads three public files from `SITE_URL/data/record/views/` (`track-record.json`, `manifest.json`, `health/settle-tick.json`) and builds the board `evaluateSettle` already takes (`settleFromRecord`): tick stale after 3 days of no heartbeat, the views stale after 9 hours (their own rhythm, not the old file's 6). With no heartbeat yet the check waits (`skipped`) instead of alerting.

### 5. The forecasts view and the three live readers
- **`record/views/forecasts/<threadId>.json`**: the story view's `forks` (with `scoring`, `state`, verdicts) in a file of its own, for each story that has drawn a question; empty for a story that was merged into another. Schema `schema/views/forecasts.schema.json`. The manifest says `forecastViews: <n>`; a page takes a missing file to mean "no forecast" only when the manifest has the field (a build before this one wrote none).
- **Mapper.** `frontend/src/shared/lib/forecastFromView.js` (moved from `features/threads/lib/viewForecast.js`; byte-identical copy in `newsSharedAnalysis`, checked by `scripts/check-shared-sync.mjs`) maps forks to the `prediction_snapshot` shape; its live-capture tests (20 stories) pass unchanged.
- **Readers**, each record first while the views are fresh (0050), the action as the fallback: `useStoryQuestion` (briefing slide), `useCountryStories` (country card deadlines: the newest forecast among the card's stories, one view per story, `countryForecast`), and the analysis context (`fetchers.forecastFromRecord`, wired in `newsSharedAnalysis` when `RECORD_VIEWS_URL` is set). The story page keeps its own order (story view, then the action), see "Not retired".

## Consequences

The refresh of 0050 adds today's *entries* provisionally, not today's forecasts. Follow-up built and deployed 2026-11-01: the refresh turns today's forecasts-inbox lines (its own prefix, never a PredictionLog Scan) into provisional `forecast_drawn` facts, as it does for entries; the nightly fact of the same row has the same `eventId` (sha1 of kind + `PRED#<topic>|<day>`) and replaces it; forks carry `provisional: true` and the manifest `provisionalForecasts`. The story page, briefing, country card and `newsSharedAnalysis` now read the record only (frontend released 2026-11-01; `newsSharedAnalysis` has `RECORD_VIEWS_URL` set).
- The resolver's watch and draw, `newsStoryRecord` and the monitor can run with no `PRED#` read once `FORECASTS_SOURCE=inbox`, `QUESTIONS_SOURCE=record`, `SETTLE_SOURCE=record`. All three are live: `SETTLE_SOURCE=record`, `FORECASTS_SOURCE=inbox` since 2026-11-02 and `QUESTIONS_SOURCE=record` since 2026-11-02 ~13:40Z. Only the agent still reads and writes `PRED#` (put, reconcile, `readThreadForks`) until step 5 deletes them.
- The IAM change: the resolver's heartbeat needs one more key (below); the agent needs the inbox prefix; the monitor and `newsStoryRecord` need none.
